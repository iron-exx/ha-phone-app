# Phase 3: QR Provisioning & Device Management — Plan 05

**Wave:** 1 (fifth plan wave)
**Goal:** Implement the app-side provisioning flow — from QR code scanning through to device setup and Push-Token registration on both iOS and Android.

## Scope

This plan covers the mobile app implementation of the QR provisioning flow. Users open the app, scan a QR code, and the device gets fully provisioned (SIP credentials + Push-Token registered) without any manual data entry.

## Plans within this Wave

### Plan 05-01: QR-Scanner Screen (iOS — SwiftUI)
**Task 1:** Implement Camera Preview with Overlay Frame.
- Use `AVFoundation` `AVCaptureSession` for camera input
- Overlay: gerahmtes Rechteck im Zentrum, QR-Code sollte darin erkannt werden
- Task 2: QR Code Detection using `Vision` framework `VNDetectBarcodesRequest`.
- Supported Formate: `haphone://provision?t=<JWT>` und Universal Links `https://.../app/setup?t=<JWT>`
- Task 3: After Detection: JWT von Query-Parameter extrahieren, auf Signature (`exp`, `jti`, `purpose`) validieren
- Task 4: Bei Validierung: `POST /api/mobile/provision/start` mit JWT im Body oder Header (je nach API-Design)
- Task 5: Response parsen: `pbx_url`, `sip_domain`, `extension`, `codecs`, `cert_bundle_pem` etc. in "Ready Screen" darstellen
- Task 6: "Weiter" Button → `POST /api/mobile/provision/complete` mit `{push_token, device_id, app_platform: "ios"}`
- Task 7: Bei Success: "Eingerichtet als Extension [Nummer] [Name]" Screen mit "Testanruf starten" Button
- **Done when:** Scanner erkennt QR → JWT validiert → Config geladen → Push-Token registriert → Success Screen mit Outgoing Call UI

### Plan 06-02: QR-Scanner Screen (Android — Jetpack Compose)
**Task 1:** Use Android `CameraX` Library für Camera Preview.
- Task 2: Barcode Detection mit `ML Kit Barcode Scanning` oder `Vision` API Äquivalent.
- Task 3: Same detection/validation flow as iOS: JWT extrahieren, `exp`/`jti`/`purpose` prüfen
- Task 4: `POST /api/mobile/provision/start` aufrufen mit Config-Response parsen
- Task 5: Push-Token via `Firebase Messaging` registrieren — in `onMessageReceived` den Token speichern
- Task 5: `POST /api/mobile/provision/complete` mit `{push_token, device_id: os_android_id, app_platform: "android"}`
- Task 6: Success Screen: "Eingerichtet als Extension [Nummer] [Name]" + "Testanruf starten"
- **Done when:** Android Scanner erkennt QR → JWT validiert → Config geladen → FCM Token registriert → Success Screen

### Plan 07-03: Config Parsing & SIP-Parameter verarbeiten (Shared)
**Task 1:** Shared Data Models für both Platforms.
- iOS: Swift Structs `@MainActor`; `@Published` Properties für: `pbxUrl: String`, `sipDomain: String`, `extensionNumber: String`, `codecs: [String]`, `certificatePem: String`, `expiresAt: Date`
- Android: Kotlin data classes mit `@Composeable` Zustands-Management; `StateFlow` für gleiche Properties
- Task 2: Both from same OpenAPI-generated client — consistency guaranteed
- Task 3: "Ready Screen" UI: PBX-URL anzeigen (kann obscured werden), Extension-Nummer, Gerätename, Codecs-Auswahl (Checkboxen: Opus, G.722, G.711)
- Task 4: "Weiter" Button ist disabled bis alle Felder valide sind (mindestens ein Codec ausgewählt, PBX-URL beginnt mit `sips://` oder `https://`)
- **Done when:** Both Platforms können Config parsen und "Ready Screen" darstellen mit validen Daten

### Plan 08-02: Push-Token Registrierung (iOS — PushKit)
**Task 1:** `PKPushRegistry` setup in `AppDelegate` oder `SwiftUI` `LifeCycle`.
- Task 2: `.voIP` Push-Type registrieren
- Task 3: Bei eingehendem Push: `pushRegistry(_:didReceiveIncomingPushWith:for:completion:)` — hier nicht für Provisioning nutzen (das ist ein anderer Flow)
- Task 3: Eigenen Method `registerPushToken(token: Data)` die `POST /provision/complete` aufruft
- Task 4: `PushToken` aus ` pushRegistry(_:didUpdate:for:)` beziehen
- Task 4: Error Handling: `.badToken`, `.invalidConfiguration` → Toast "Push-Berechtigung fehlerhaft — Einstellungen öffnen"
- **Done when:** iOS App kann ihr eigenes Push-Token an HA-Phone Relay über `/provision/complete` registrieren; Errors werden gefangen und user-freundlich angezeigt

### Plan 09-01: Push-Token Registrierung (Android — FCM)
**Task 1:** `FirebaseMessagingService` überschreiben, `onMessageReceived` für high-priority data messages abfangen.
- Task 2: Nicht für App-Visibility prüfen — dieser Flow läuft unabhängig (App im Vordergrund, Hintergrund oder getötet)
- Task 3: `String pushToken = FirebaseInstanceId.instance.id` (oder aktuelles `InstanceIdManager`)
- Task 3: `POST /api/mobile/provision/complete` mit `{push_token: string, device_id: string, app_platform: "android"}`
- Task 4: Response validieren: `{success: true, device_cert_fingerprint}`
- Task 5: Bei Success: `state.value = "provisioned"` und Outgoing Call UI enable
- **Done when:** Android App registriert Push-Token bei HA-Phone; Success führt zu Outgoing Call UI; Fehler → Toast "Provisionierung fehlgeschlagen — erneut versuchen"

### Plan 10-02: Success Screen & Outgoing Call Enable (both Platforms)
**Task 1:** After `/provision/complete` Success: UI State ändern von `"unprovisioned"` zu `"provisioned"`.
- Task 2: "Testanruf starten" Button enable; Navigation zum Dialpad/Outgoing Call Screen
- Task 3: Device lokal speichern als "provisioned" in UserDefaults (iOS) / SharedPreferences (Android) mit Ablauf-Datum (`expires_at` aus JWT)
- Task 4: Bei App-Neustart: Device-Status prüfen — wenn `expires_at` noch gültig → Outgoing Call UI sofort enable; wenn abgelaufen → "Neu provisionieren" Button zeigen
- Task 5: Outgoing Call: SipSession zu HA-Phone Extension aufbauen (aufbauend auf Phase 2 Wissen: transient registration, CALL-03/05)
- **Done when:** Nach erfolgreicher Provisionierung: Outgoing Call UI sofort verfügbar; Device-Status überlebt App-Neustart (sofern Token nicht abgelaufen); "Neu provisionieren" bei Ablaut führt zu neuem QR-Flow

## Exit Criteria

- QR-Scanner auf beiden Plattformen funktioniert end-to-end: Scan → Config → Push-Register → Success
- Outgoing Call UI ist nach Provisionierung sofort verfügbar
- Device-Status überlebt App-Neustart (sofern Token noch gültig)
- User kann bei Token-Ablauf "Neu provisionieren" antippen und neuen QR-Scan Flow starten
