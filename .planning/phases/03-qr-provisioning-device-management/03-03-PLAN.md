# Phase 3: QR Provisioning & Device Management — Plan 03

**Wave:** 1 (third plan wave)
**Goal:** Implement device-level management operations: lock, delete, regenerate QR, refresh certificate — with proper validation and user confirmation flows.

## Scope

This plan continues the Dashboard UI from Plan 02, focusing on the actual management operations for individual devices. Each plan covers one management operation with its API backend integration and UI flow.

## Plans within this Wave

### Plan 03-01: Gerät sperren (Lock Device) — Vertiefung aus Plan 02-03
**Task 1:** Same as Plan 02-03 but with additional validation.
- Before lock: Check if device has active call → Warnung: "Gerät hat aktiven Anruf — Sperren verhindert bis Anruf beendet"
- After lock: Auto-logout von SIP-Session falls aktiv; Device-Status auf "locked" setzen; Toasts je Outcome
- Task 2: "Entsperren" mit gleicher Validierung (Check: Device darf gesperrt sein bevor entsperrt wird)
- **Done when:** Lock/Unlock mit Validierung von Call-State; UI blockiert bei aktivem Anruf; Feedback-Toasts sind spezifisch

### Plan 04-02: Gerät löschen (Delete Device) — Vertiefung aus Plan 02-04
**Task 1:** Same as Plan 02-04 mit erweiterter Bestätigung.
- Bestätigungs-Modal enthält: Device-Name, Extension-Nummer, "Alle Zertifikate werden widerrufen", "Dies kann nicht rückgängig gemacht werden"
- Task 2: Nach Löschung: Device aus Liste entfernen; Toast "Gerät gelöscht — Adminsitzung kann erforderlich für neue Provisionierung"
- **Done when:** Löschung erfordert ausdrückliche Bestätigung mit Device-Details; nach Löschung Complete-Remove aus UI

### Plan 05-03: Neuen QR-Code generieren (Regenerate QR) — Vertiefung aus Plan 02-05
**Task 1:** Same as Plan 02-05 aber mit Option "Sofort neu provisionieren".
- Nach QR-Generierung: Offerte "Jetzt scannen" → App öffnet QR-Scanner automatisch mit neu generiertem Code (Deep-Link)
- Task 2: Offerte "Später scannen" → QR-Code im Dashboard sichtbar; User scannet manuell später
- **Done when:** "Jetzt scannen"-Option öffnet Scanner mit prä-filled JWT; "Später scannen" zeigt QR im Dashboard; Beide Wege führen zu erfolgreicher Neu-Provisionierung

### Plan 06-04: Zertifikat erneuern (Refresh Certificate) — Vertiefung aus Plan 02-06
**Task 1:** Same as Plan 02-06 mit Fehler-Handling bei abgelaufenem alten Zert.
- Wenn altes Zert bereits abgelaufen: Warning "Altes Zertifikat ist abgelaufen — Rotation kann fehlschlagen"
- Task 2: Rollback-Option: "Auf altes Zertifikat zurücksetzen wenn Neue Rotation fehlschlägt"
- **Done when:** Rotation fehlgeschlagen → User kann auf altes Zert zurücksetzen; UI zeigt Rot/Warning bei Zert-Problemen

### Plan 07-05: Test-Push senden (Send Test Push) — Vertiefung aus Plan 02-07
**Task 1:** Same as Plan 02-07 mit Status-Polling.
- Nach Senden: Dashboard zeigt Countdown "Zustellung in 10s..." dann "Zugeliefert" oder "Keine Zustellung"
- Task 2: History-Log: Jeder Test-Push wird protokolliert mit Timestamp, Resultat, Admin-Name
- **Done when:** Test-Push History im Dashboard einsehbar (letzte 5 Tests); Jeder Eintrag hat Timestamp + Resultat + Admin-Name

## Exit Criteria

- Alle 7 Sub-Pläne funktionieren einzeln und in Folge
- Jeder API-Endpunkt hat valid Response-Format und Error-Handling
- UI-Toasts sind spezifisch für jede Aktion und Outcome
- Fehler-Cascades werden verhindert (z.B. Lock verhindert bei aktivem Anruf)
