# Phase 3: QR Provisioning & Device Management — Plan 02

**Wave:** 1 (second plan wave)
**Goal:** Implement the HA-Phone Dashboard UI for device management — admin can view, lock, delete, and re-provision devices per extension.

## Scope

This plan covers the admin-facing UI side of Phase 3. The provisioning flow (QR scan + app setup) from Plan 01 is assumed complete. Now the admin needs tools to manage devices.

## Plans within this Wave

### Plan 02-01: Dashboard Layout — Geräte-Liste pro Extension
**Task 1:** Implement Dashboard screen showing devices per extension.
- UI: TabView/SegmentedControl mit Extension-Liste; jede Extension zeigt Device-Karte an
- Spalten: Gerätename, Plattform-Icon (iOS/Android), Status-Indikator (Grün/Gelb/Rot), Letzter Kontakt (Datum/Uhrzeit), Zertifikat-Ablauf (Tage bis Ablauf)
- Horizontal Scrollable, wenn viele Geräte pro Extension
- **Done when:** Dashboard lädt Device-Daten von HA-Phone Backend (`GET /api/mobile/devices?extension=123`) und zeigt korrekte Spalten an

### Plan 02-02: Device Card — Aktionen und Status
**Task 1:** Design Device Card component with status and actions.
- Header: Gerätename + Plattform-Icon
- Status Badge: Grün (Online + Push OK), Gelb (Online aber Push-Probleme), Rot (Offline), Grau (Sperren/Löschen)
- Footer mit Aktions-Buttons (bedingt sichtbar je nach Status):
  - "Sperren" (DeviceStatus=aktiv)
  - "Entsperren" (DeviceStatus=gesperrt)
  - "Löschen" (DeviceStatus=aktiv)
  - "Neuen QR-Code erzeugen" (beliebiges Device)
  - "Zertifikat erneuern" (beliebiges Device)
  - "Test-Push senden"
- **Done when:** Device Card klickbar; Buttons triggern respective API-Calls; Status ändert sich visuell

### Plan 02-03: Aktion: Gerät sperren/ent-sperren
**Task 1:** Implement "Sperren" Action.
- POST `/api/mobile/device/{id}/lock` → Response: `{ success: true, device_status: "locked" }`
- Device Card: Status Badge wechselt von Grün nach Gelb/Rot (je nach vorherigem Status)
- Toasts: "Gerät gesperrt — bei nächsten Anruf nicht mehr klingeln"
- Task 2: Implement "Entsperren" Action.
- POST `/api/mobile/device/{id}/unlock` → Response: `{ success: true, device_status: "active" }`
- Device Card: Status Badge wechselt zurück zu Grün
- Toasts: "Gerät entsperrt — klingelt wieder bei Anrufen"
- **Done when:** Lock/Unlock funktioniert via API; UI aktualisiert sich ohne Page-Refresh (WebSocket/Long-Poll oder Polling alle 5s)

### Plan 02-04: Aktion: Gerät löschen
**Task 1:** Implement "Löschen" Action.
- POST `/api/mobile/device/{id}/delete` → Response: `{ success: true, device_deleted: true }`
- Modal Bestätigung: "Wirklich löschen? Dieses Gerät wird aus der Extension entfernt. Alle Zertifikate werden widerrufen. Aktion kann nicht rückgängig gemacht werden."
- Nach Bestätigung: Device Card entfernt sich selbst aus Liste (oder wird mit Status "gelöscht" ausgeblendet)
- Toasts: "Gerät gelöscht — Zertifikat wurde widerrufen"
- **Done when:** Lösch-Modal erscheint; nach Bestätigung Device aus Liste verschwunden; Backend aktualisiert Device-Status auf "gelöscht" und widerruft mTLS-Cert via CRL

### Plan 02-05: Aktion: Neuen QR-Code erzeugen
**Task 1:** Implement "Neuen QR-Code erzeugen" für bestehendes Device.
- POST `/api/mobile/device/{id}/regenerate-qr` → Response: `{ new_jwt, new_expires_at, qr_code_svg oder uri }`
- Modal: "Neuer QR-Code wurde generiert. Scannen Sie den neuen Code, um das Gerät neu zu provisionieren. Der alte QR-Code ist ungültig."
- Zeige neuen QR-Code als SVG/Custom Scheme Link an
- Toasts: "Neuer QR-Code generiert — alter Code ist ungültig"
- Task 2: Automatische Neu-Provisionierung optional (oder manuell).
- Optional: App erkennt neuen JWT automatisch beim nächsten Start (Background-Refresh)
- **Done when:** Admin kann neuen QR für bestehendes Device generieren; QR-Code wird angezeigt; App muss neu gescannt werden (oder im Hintergrund aktualisieren)

### Plan 02-06: Aktion: Zertifikat erneuern
**Task 1:** Implement "Zertifikat erneuern" Action.
- POST `/api/mobile/device/{id}/refresh-cert` → Response: `{ new_cert_bundle_pem, new_cert_expires_at, rotation_success: true }`
- Zertifikats-Rotation: Neues mTLS-Zertifikat wird von HA-Phone CA ausgestellt; altes wird via CRL widerrufen
- Task 2: App lädt neues Zertifikat herunter und installiert in Keychain/Keystore.
- Background Task: App prüft bei Start ob Zertifikat bald abläuft (z.B. < 30 Tage) und zeigt Badge "Zertifikat erneuern verfügbar" an
- User klickt → API-Call → Zertifikat wird ersetzt ohne Neu-Provisionierung
- **Done when:** Zertifikat kann per API erneuert werden; App installiert neues Zertifikat; Gültigkeit auf 90 Tage zurückgesetzt; Kein erneuter QR-Scan nötig

### Plan 02-07: Test-Push senden
**Task 1:** Implement "Test-Push senden" Action.
- POST `/api/mobile/device/{id}/test-push` → Response: `{ success: true, sent_at, delivered_at?: null }`
- Flow: Backend sendet signierten Test-Push (Event-Type=test) an APNs (iOS) / FCM (Android)
- Task 2: App empfängt Push und zeigt Toast/Notification: "Test-Push empfangen von HA-Phone"
- Task 3: Dashboard zeigt Lieferstatus: "Gesendet vor 2s", "Zugeliefert", "Keine Zustellung (App im Vordergrund?)" 
- **Done when:** Test-Push kann von Admin gesendet werden; App empfängt und zeigt Feedback; Dashboard zeigt Live-Status

## Exit Criteria

- Admin kann alle Device-Aktionen aus dem Dashboard durchführen: Sperren/Entsperren, Löschen, Neuen QR generieren, Zertifikat erneuern, Test-Push senden
- Alle API-Endpunkte reagieren mit validen Responses und aktualisieren UI sofort
- Fehlgeschlagene Aktionen zeigen spezifische Error-Toasts (nicht generisch "Fehler aufgetreten")
- Dashboard reflektiert Device-Status-Änderungen in Echtzeit (bzw. nach kurzem Refresh)
