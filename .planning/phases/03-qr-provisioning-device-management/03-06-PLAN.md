# Phase 3: QR Provisioning & Device Management — Plan 06

**Wave:** 1 (sixth plan wave)
**Goal:** Error handling, edge cases, and recovery flows for the app-side provisioning and device management system.

## Scope

This plan covers what happens when the provisioning flow encounters problems — network failures, invalid QR codes, expired tokens, and user cancellation. The goal is graceful degradation and clear user feedback.

## Plans within this Wave

### Plan 06-01: Invalid/Expired QR Code Handling
**Task 1:** QR-Code kann nicht decodiert werden (kein gültiges Format).
- Scan-Versuch: `AVFoundation` / `ML Kit` liefert kein Ergebnis oder Fehlermeldung
- UI: Toast "'Ungültiger QR-Code' — bitte scannen Sie den von Admin generierten Code"
- Task 2: "Code erneut anfordern" Button → Leitet zu Dashboard weiter (oder Pull-to-Refresh auf Scanner-Screen)
- Task 3: nach 3 fehlgeschlagenen Scans: "Zu viele Fehlversuche — bitten Sie Admin, einen neuen QR-Code zu generieren"
- **Done when:** Invalid QR wird gefangen; User zur Neu-Beschaffung geleitet; nach 3 Attempts klarer Hinweis

### Plan 07-02: Abgelaufener JWT während Provisioning (Expired Token)
**Task 1:** User scannt QR-Code, aber `exp` Claim ist bereits vergangen (TTL 5 Min überschritten).
- Detection: JWT Library parse erfolgreich, aber `exp < Date()`
- UI: Toast "'QR-Code abgelaufen (5 Min)' — Admin muss neuen generieren"
- Task 2: "Admin kontaktieren" Button → öffnet Dashboard (oder tiefenlinkt zur "Mobilgerät hinzufügen" Seite)
- Task 3: Admin Dashboard zeigt Countdown "QR-Code abläuft in X Min" für dieses Device
- **Done when:** Abgelaufener JWT erkannt; User wird zur Neu-Beschaffung geleitet; Admin sieht Timer

### Plan 08-03: Netzwerkfehler während App-Side Provisioning (Network Error)
**Task 1:** Kein Internet beim `POST /provision/start` oder `POST /provision/complete`.
- Catch: `URLError` (iOS) / `UnknownHostException` / keine Konnektivität
- UI: Toast "Netzwerkfehler — bitte Verbindung prüfen und 'Retry' drücken"
- Task 2: Request lokal zwischenspeichern (UserDefaults/iCloud sync-fähig oder SQLite) mit Timestamp
- Task 3: Background Task (iOS: `BackgroundFetch`; Android: `WorkManager`) versucht Request alle 30s erneut (max 3 Versuche mit exponentiellem Backoff)
- Task 4: Nach 3 fehlgeschlagenen Versuchen: "Provisionierung fehlgeschlagen — Support-Code kopieren" mit Error-ID, Timestamp, Request-Type
- **Done when:** Network Error gefangen; Local Storage von Request; Background Retry Logik; Nach 3 Fehlern klarer Fehler-Status

### Plan 09-03: Device State Konflikt (Device State Conflict)
**Task 1:** Dashboard/ App zeigt `status: "active"` aber Admin hat Device per API gesperrt/gelöscht (State Divergenz).
- Detection: Periodisches Pull (`every 30s`) oder WebSocket Long-Poll Response hat anderen Status als lokaler Cache
- UI: Alert "Device Status aktualisiert — App neu laden?" mit Optionen: "Jetzt neu laden" / "Später erinnern (5 Min)"
- Task 2: Force Refresh zieht aktuellen Status von HA-Phone Backend (`GET /api/mobile/devices/{id}`)
- Task 3: Wenn Device gesperrt → UI deaktiviert Sperren-Button; zeigt "Gesperrt" Badge; wenn gelöscht → Device aus Liste entfernen, Toast "Device wurde von Admin gelöscht"
- **Done when:** State Divergenz erkannt; Force Refresh funktioniert; UI reflects aktuellen Backend-Status

### Plan 10-04: Concurrent Operations (Gleiche Aktion doppelt tippen)
**Task 1:** User tippt "Sperren" oder "Test-Push senden" zweimal innerhalb von 2 Sekunden.
- Task 2: Erste Request ist noch nicht retour → zweite Request sollte `disabled` Zustand zeigen oder zweite Request ignorieren mit Toast "Bereits im Prozess — bitte warten"
- Task 2: After-first-Response: UI aktualisiert sich basierend auf erstem Outcome; zweite Request liefert Outcome-basierten Status oder Error "Bereits ausgeführt"
- **Done when:** Doppelte Requests graceful behandelt; Kein doppeltes Sperren/Löschen/ Push; User sieht Fortschritts-Status

## Exit Criteria

- Alle Edge Cases werden gefangen und zeigen user-friendly Meldungen
- Kein Absturz bei Netzwerk-Fehlern, Parse-Fehlern, State-Konflikten
- Recovery-Loops (Retry, Force Refresh, Fallback) funktionieren korrekt
- User versteht jeden Fehler und weiß nächste Schritte
