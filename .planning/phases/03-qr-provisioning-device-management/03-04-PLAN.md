# Phase 3: QR Provisioning & Device Management — Plan 04

**Wave:** 1 (fourth plan wave)
**Goal:** Handle edge cases, error scenarios, and recovery flows for the provisioning and device management system.

## Scope

This plan covers what happens when things go wrong — network failures, expired tokens, invalid QR codes, device state conflicts — and how the system recovers gracefully.

## Plans within this Wave

### Plan 04-01: Abgelaufener QR-Code behandeln (Expired QR Code)
**Task 1:** QR-Code ist abgelaufen (5 Min TTL erreicht).
- Scan-Versuch: JWT `exp` Claim < now()
- UI: Toast "'QR-Code abgelaufen (5 Min)' — Bitte neuen QR-Code von Admin anfordern"
- Task 2: Admin Dashboard zeigt "QR-Code abläuft in X Min" Countdown an
- Task 3: "Neu scannen" Button löst neuen QR-Code Request aus (POST `/provision/start`)
- **Done when:** Abgelaufener QR wird erkannt; User wird zur Neu-Beschaffung geleitet; Admin sieht Ablauf-Timer

### Plan 05-02: Ungültiger/beschädigter QR-Code (Invalid QR Code)
**Task 1:** QR-Code kann nicht decodiert werden (kein gültiges URI/kein JWT).
- Scan-Versuch: Parse Fehler — kein gültiges `haphone://provision?t=` oder Universal Link
- UI: Toast "Ungültiger QR-Code — bitte scannen Sie den von Admin generierten Code"
- Task 2: "Code erneut anfordern" Button → Admin Dashboard Refresh → Neuen QR generieren
- **Done when:** Parse-Fehler werden gefangen; User zur Neu-Beschaffung geleitet; Kein Absturz der App

### Plan 06-03: Netzwerkfehler während Provisioning (Network Error)
**Task 1:** Kein Internetzugriff beim `/provision/start` Call.
- Catch: `URLError` (iOS) / `UnknownHostException` (Android)
- UI: Toast "Netzwerkfehler — bitte Verbindung prüfen und 'Retry' drücken"
- Task 2: Retry speichert Config-Request lokal (Background-Fetch/WorkManager) und versucht es alle 30s erneut (max 3 Versuche)
- Task 3: Nach 3 fehlgeschlagenen Versuchen: "Provisionierung fehlgeschlagen — Support-Code kopieren" mit Error-ID, Timestamp, Request-Type
- **Done when:** Network Error wird gefangen; Retry-Logik funktioniert; Nach 3 Fehlschlägen klarer Fehler-Status

### Plan 07-04: Device-Status-Konflikt (Device State Conflict)
**Task 1:** Device Status widerspricht tatsächlichem Zustand (z.B. Dashboard zeigt "aktiv" Device wurde aber per Admin gesperrt/gelöscht).
- Detection: WebSocket Long-Poll Response hat `status: "locked"` aber Local Cache hat `status: "active"`
- UI: Alert "Device Status aktualisiert — App neu laden?" mit Optionen: "Jetzt neu laden" / "Später erinnern"
- Task 2: Force Refresh zieht aktuellen Status von HA-Phone Backend (`GET /api/mobile/devices/{id}`)
- Task 3: Wenn Device gesperrt/gelöscht → UI aktualisiert und deaktiviert Aktionen die nicht mehr möglich sind (Sperren-Button ausgeblendet bei gesperrtem Device)
- **Done when:** Status-Konflikt wird erkannt; Force Refresh funktioniert; UI reflects aktuellen Status von Backend

### Plan 08-05: Concurrent Device Operations (Gleiche Aktion doppelt)
**Task 1:** User betätigt "Sperren" zweimal schnell hintereinander.
- Task 2: Erste Request ist noch nicht retour → zweite Request sollte "disabled" Zustand zeigen oder zweite Request ignorieren mit Toast "Bereits im Prozess — bitte warten"
- Task 2: After-first-Response: UI aktualisiert sich basierend auf erstem Outcome; zweite Request liefert Outcome-basierten Status
- **Done when:** Doppelte Requests werden graceful behandelt; Kein doppeltes Sperren/Löschen; User sieht Fortschritts-Status

### Plan 08-06: Zertifikats-Rotation fehlgeschlagen (Cert Rotation Failure)
**Task 1:** Neue Zertifikats-Rotation schlägt fehl (z.B. CA nicht erreichbar, Keychain Permission entzogen).
- Task 2: UI zeigt "Zertifikats-Rotation fehlgeschlagen — auf altes Zertifikat zurückgekehrt" + "Einstellungen öffnen" Button (führt zu iOS Settings Keychain oder Android Settings Security)
- Task 3: User kann manuell Zertifikat neu installieren (falls sie Permission erlaubt hat) oder Admin kann Rotation neu versuchen
- **Done when:** Rotation-Failure wird gefangen; User wird auf richtige Settings weitergeleitet; Fallback auf altes Zertifikat funktioniert

### Plan 09-07: Offline-Queue für Provisioning (Offline Queue)
**Task 1:** User startet Provisioning ohne Internet (Airplane Mode oder kein Netzwerk).
- Task 2: App speichert Provisioning-Request lokal (UserDefaults/iCloud sync-fähig oder SQLite) mit Timestamp und JWT
- Task 3: Sobald Netzwerk zurückkehrt: Background Task sendet alle gespeicherten Requests nach (max 5 Attempts, exponential backoff)
- Task 4: UI zeigt "Provisionierung im Hintergrund — zuletzt versucht um HH:MM" an
- **Done when:** Offline-Request wird lokal gespeichert; Nach Netzwerk-Return wird automatisch gesendet; UI zeigt Status an

## Exit Criteria

- Alle Edge Cases werden gefangen und zeigen user-friendly Meldungen
- Kein Absturz bei Netzwerk-Fehlern, Parse-Fehlern, State-Konflikten
- Recovery-Loops (Retry, Force Refresh, Fallback) funktionieren korrekt
- Offline-Queue funktioniert bei App-Neustart nach Netzwerk-Return
