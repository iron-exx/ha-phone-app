# Phase 4: Call-State Orchestration, Multi-Device Race & Diagnostics — Plan 01

**Wave:** 1 (first plan wave)
**Goal:** Implement the PBX call-state machine that authoritative controls multi-device ringing — all devices registered to one extension ring on an incoming call, the first device to answer wins, and all other devices receive an immediate cancel push to stop ringing.

## Scope

This plan covers the server-side call-state machine in HA-Phone (Asterisk/FastAPI) and the client-side app logic that reacts to state changes. The core problem: without authoritative call state, all devices ring until someone answers, then there's a race condition where multiple devices are in an active call, or calls get confused.

## Plans within this Wave

### Plan 04-01: PBX Call-State Machine — Core Logic
**Task 1:** Add `call_state` field to the Trunk/Extension model in HA-Phone (`models.py`).
- Values: `idle`, `ringing`, `active`, `held`, `cancelled`, `transferring`
- Task 2: When an inbound call arrives via Asterisk, set Extension `call_state` to `ringing` and initiate multi-device ring pattern.
- Task 3: When first device answers (SIP 200 OK), set `call_state` to `active`, cancel ringing on all other devices via `PJSIP/cancel` or Asterisk `Local/SimplePosition` dialplan.
- Task 4: When call is hung up, set `call_state` to `idle` and clean up.
- **Done when:** Call state transitions are visible via Asterisk CLI (`pjsip show endpoints`) and REST API (`GET /api/calls/{callId}`).

### Plan 04-02: Multi-Device Ring Pattern
**Task 1:** When `call_state` = `ringing`, Asterisk/FastAPI sends a ring signal to all Devices registered to that Extension (via existing Push-Relay or direct APNs/FCM).
- Task 2: Each Device receives the incoming-call push; app shows native call UI (CallKit iOS / Telecom Android).
- Task 3: When first device answers, send `POST /api/calls/{callId}/cancel` to HA-Phone Backend; Backend sets `call_state` = `active` and sends cancel push to all remaining ringing devices.
- Task 4: Cancel push payload: `{ cancel: true, callId, fromDeviceId }` — receiving app hides call UI and returns to dialpad.
- **Done when:** Ring pattern works: all ring → first answer → others cancel → active call established on answering device only.

### Plan 04-03: Call-ID Generation & Central Management
**Task 1:** Every inbound call gets a unique, globally unique Call-ID (UUID v4, stored in Asterisk channel variable and HA-Phone DB).
- Task 2: Call-ID is passed in every push payload, cancel payload, and API response.
- Task 3: No two concurrent calls share the same Call-ID; Call-ID is the single source of truth for call state.
- **Done when:** UUID generated, stored, and propagated correctly through the entire call flow (Asterisk → FastAPI → Push → Apps).

## Exit Criteria

- Call state machine transitions correctly through: `idle` → `ringing` → `active` → `idle`
- When first device answers, all other ringing devices receive cancel push and stop ringing
- Call-ID is unique per call and propagated through all layers (Asterisk → FastAPI → Push → App)
- API `GET /api/calls/{callId}` returns correct `call_state`, `device_id`, `timestamp`
