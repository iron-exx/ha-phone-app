# Phase 4: Call-State Orchestration, Multi-Device Race & Diagnostics — Plan 02

**Wave:** 1 (second plan wave)
**Goal:** Implement the multi-device ring pattern and cancel logic — when one device answers, all other ringing devices must stop immediately via server-triggered cancel push.

## Scope

This plan focuses on the ring coordination between multiple devices registered to the same Extension. The PBX call-state machine (Plan 04-01) tracks state, but this plan implements the actual ring coordination and cancel delivery.

## Plans within this Wave

### Plan 04-01 (continued): Cancel Push Delivery
**Task 1:** When `call_state` transitions from `ringing` to `active` (first device answered), Backend sends cancel push to all Devices registered to that Extension except the answering device.
- Task 2: Cancel push payload structure: `{ cancel: true, callId, fromDeviceId: answeringDeviceId }`
- Task 3: App receives cancel push; `onPushReceived` handler hides native call UI, returns to dialpad/main screen.
- Task 4: User visible effect: calling devices' call screens fade/dismiss immediately; dialpad becomes active.
- **Done when:** Cancel push delivered to all non-answering devices; UI dismisses on all but one device.

### Plan 04-03: Race Condition Prevention
**Task 1:** Ensure only one device can answer first — the `call_state` machine prevents a second device from answering after the first answer.
- Task 2: When Device A answers (SIP 200 OK), Backend sets `call_state` = `active` and immediately sends cancel to all other Devices.
- Task 3: If Device B attempts to answer within the cancel window (≤ 2s), Backend rejects with `409 Conflict` and Device B's SIP `INVITE` is declined locally.
- Task 4: User on Device B sees: "Anruf wurde beendet — bereits von anderem Gerät angenommen" Toast.
- **Done when:** Second device cannot answer after first answer; cancel window is ≤ 2s; User feedback is clear.

### Plan 04-04: Timeout for No Answer
**Task 1:** If no device answers within 30 seconds, `call_state` automatically transitions from `ringing` to `cancelled`.
- Task 2: All devices receive a "missed call" push (different from cancel push — this is a notification that the call expired).
- Task 3: Call-ID remains active for CDR (Call Detail Record) purposes; can be referenced in logs.
- **Done when:** 30-second timeout fires; all devices get missed-call push; call_state = `cancelled`.

### Plan 04-05: Hold & Resume (Basic Support)
**Task 1:** When user presses "Hold" on the active call, `call_state` transitions from `active` to `held`.
- Task 2: Other devices registered to the same Extension still see `call_state` = `held` — their call UI shows "On Hold" indicator.
- Task 3: When user presses "Resume", `call_state` transitions back to `active`; all devices' UI returns to active call state.
- **Done when:** Hold/Resume transitions work; state consistent across all registered devices.

## Exit Criteria

- First device answers → all other devices receive cancel push → their call UI dismisses
- If no answer within 30s → call_state → `cancelled`; all devices get missed-call push
- Hold/Resume transitions work and state is consistent across all devices registered to the same Extension
- Second device attempting to answer after first answer is rejected with clear user feedback
