## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Firebase service-account key -> tools/push_trigger.py | A long-lived, highly privileged credential (can send to any device registered to the project) lives on the developer's local disk |
| Self-managed ConnectionService registration -> OS full-screen-intent auto-grant (no Play Console declaration, D-12) | Whether Android 14+ grants full-screen call display to a sideloaded, non-Play-declared calling app is being tested empirically rather than assumed either way |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-03 | Elevation of Privilege | tools/keys/firebase-service-account.json, android-app/app/google-services.json | mitigate | Both gitignored (Task 2's `.gitignore` update + Plan 01's existing `tools/keys/*` pattern); `git check-ignore` assertion in acceptance criteria |
| T-01-04 | Information Disclosure | FCM token displayed in MainActivity UI | accept | The token is device- and app-scoped, not a secret capable of impersonating the sender; displaying it on a physical device the developer controls for manual copy-paste is low risk for a single-developer Phase 1 prototype |
| T-01-07 | Denial of Service (of feature, not a security exploit) | Self-managed ConnectionService full-screen-intent grant, absent any Play Console "calling app" declaration | accept | Per D-12, this is a deliberate zero-budget trade-off: if the OS denies the full-screen-intent grant to this sideloaded app, Plan 03's existing `canUseFullScreenIntent()` runtime check already provides a graceful degraded-notification fallback (confirmed in 01-03-SUMMARY.md) rather than a crash; the actual grant/deny outcome is recorded as an empirical Phase 1 finding in this plan's Task 3, not assumed working or broken in advance |
</threat_model>
