# Phase 5: Tailscale Transport Hardening — Plan 02

**Wave:** 1 (second plan wave)
**Goal:** Implement the on-demand Tailscale connection lifecycle — establish after call acceptance, maintain during call, tear down after hangup. Handle network handoffs and fallbacks.

## Scope

This plan continues the Tailscale integration from Plan 05-01, focusing on the connection management lifecycle: when to connect, when to disconnect, how to handle network changes, and what happens on edge cases.

## Plans within this Wave

### Plan 05-01 (continued): On-Demand Tailscale Connection — Detailed Flow
**Task 1:** Exact trigger moment for Tailscale establishment.
- Task 2: Not immediately after push wakeup, but after user explicitly answers the call (SIP 200 OK sent/received).
- Task 2: Trigger: `call_state` transitions from `active` (post-answer) → initiate `tailscale up` async task.
- Task 3: UI feedback: "Tailscale verbindet..." spinner in status bar or Diagnostics screen for ~5s while connection establishes.
- **Done when:** Answer → Tailscale up → ICE candidates gathered → Audio media flows over Tailscale path.

### Plan 06-02: Tear-Down After Hangup with Immediate Resource Release
**Task 1:** Exact timing for `tailscale down`.
- Task 2: Immediately after SIP BYE/200 OK exchange completes; no delay; no keepalive unless redial expected within 5 min.
- Task 3: `tailscale down` call; PJSIP ICE candidates on Tailscale interface removed; `ice-sync` reverts to previous candidate set (if fallback STUN/TURN configured).
- Task 4: Battery impact measurement: verify near-zero drain after tear-down (background Tailscale process terminated).
- **Done when:** Hangup → `tailscale down` → resources released; battery impact verified (no drain > 1%/hour in idle state after tear-down).

### Plan 07-03: Network Handoff — WiFi to Cellular (and Reverse)
**Task 1:** During active Tailscale call, user switches network (WiFi → Cellular).
- Task 2: Tailscale SDK natively handles IP re-assignment — virtual IP changes; PJSIP ICE re-gathers on new interface automatically (event: `ice-candidate-change`).
- Task 3: SIP session remains up — no SIP BYE/INVITE re-INVITE needed; the media path simply re-routes through the new Tailscale exit node/peer.
- Task 4: Brief pause (~1-2s) possible while new ICE candidates gathered; audio may have short gap but call not dropped.
- Task 5: User visible: optional status bar text change "Tailscale: connected (cellular)" vs "Tailscale: connected (WiFi)" — shown in Diagnostics screen.
- **Done when:** Network handoff triggers Tailscale re-route; PJSIP session continues; short pause possible; user optionally notified in Diagnostics.

### Plan 08-04: Fallback to STUN/TURN When Tailscale Unavailable
**Task 1:** If Tailscale key expired, revoked, or process background-killed — detect failure.
- Task 2: Detection: `tailscale status` returns error; or PJSIP ICE gathering fails on Tailscale interface; or timeout > 10s waiting for Tailscale candidate.
- Task 3: Fallback flow: App silently disables Tailscale transport; PJSIP reverts to using existing STUN/TURN candidates (configured in Phase 2 D-08 fallback config).
- Task 3: User notification: Diagnostics screen shows "Tailscale nicht verfügbar — es wird auf STUN/TURN zurückgegriffen — Erreichbarkeit may eingeschränkt"; optional Toast "Tailscale Key abgelaufen — Bitte in Settings neu eingeben".
- Task 4: Recovery: User enters new Key in Settings → app re-establishes Tailscale for next call.
- **Done when:** Tailscale unavailable → fallback activated seamlessly; user notified in Diagnostics; new Key re-enables Tailscale.

### Plan 09-05: Multi-Device Tailscale Coordination
**Task 1:** When multiple Devices registered to same Extension — each independently establishes its own Tailscale path.
- Task 2: Same Auth Key works for all; each device's Tailscale client independent; no coordination needed beyond shared Key.
- Task 3: Attended transfer scenario: Device A answers call, establishes Tailscale; Device B (waiting to join) also establishes its own Tailscale path when it joins the call; both paths coexist; media from both streams mixed at PBX level.
- Task 4: If Device B is already in call and Device A joins as attended transfer target: Device B's Tailscale path continues; Device A establishes new Tailscale path; PBX handles mixing.
- **Done when:** Multiple devices on same extension can each establish Tailscale independently; attended transfer with Tailscale works; no key conflicts.

## Exit Criteria

- Trigger moment correct: Answer → Tailscale up (not before, not after)
- Hangup → `tailscale down` with immediate resource release
- Network handoff: Tailscale re-routes automatically; PJSIP session continues
- Tailscale unavailable → fallback to STUN/TURN; user notified in Diagnostics
- Multi-device: each device independent; same Auth Key works for all; attended transfer with Tailscale functional
