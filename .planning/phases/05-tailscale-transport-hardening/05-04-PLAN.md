# Phase 5: Tailscale Transport Hardening — Plan 04

**Wave:** 1 (fourth plan wave)
**Goal:** Handle edge cases, error scenarios, and recovery flows for the Tailscale transport layer.

## Scope

This plan covers what happens when the Tailscale transport encounters problems — key expiration, process death, network changes, and fallback behavior. The goal is graceful degradation and clear user feedback.

## Plans within this Wave

### Plan 05-01 (continued): Key Expiration & Rotation Workflow
**Task 1:** Detailed workflow when Tailscale key expires mid-call or before next call.
- Task 2: Detection sequence: Background task `tailscale status` → returns `key expired` → UI status updates to `key expired` → "Key rotieren" Button enabled.
- Task 2: User taps "Key rotieren" → stored key immediately cleared from Keychain/Keystore; UI updates to `key expired` with "Neuen Key eingeben" Call-to-Action.
- Task 3: Next app launch (or immediate if foreground): Prompt "Tailscale Key abgelaufen — Bitte neuen Key eingeben" → Field for new Key → Save → Test Connection → If valid: status → `connected`; If invalid: status → `configuration error`.
- Task 4: While key expired: all Tailscale transport disabled; outgoing calls fall back to STUN/TURN (if configured); incoming calls still come via Push wakeup but audio may use relay or direct if on same LAN.
- **Done when:** Key expired → UI updates; User rotates key; New key validated; Transport re-enabled; Fallback to STUN/TURN works during expired period.

### Plan 06-01: Tailscale Process Death / Background Kill
**Task 1:** If Tailscale background process is killed by OS (Android Task Manager, iOS Background Update failure).
- Task 2: Detection: Periodic check (`every 30s`) `tailscale status` → process not running → status → `disconnected`; Or: User opens app → foreground check → status → `disconnected`.
- Task 3: UI update: Tailscale card in Diagnostics → `disconnected`; Call in progress: Tailscale transport automatically re-established in foreground (if user keeps app open) or on next outbound call attempt.
- Task 3: Call in progress: If Tailscale process dies mid-call, SIP session may degrade (media path changes from Tailscale to direct/STUN-TURN); user audible gap possible but call not dropped; `ice-candidate-change` event fires.
- Task 4: Recovery: App foreground → `tailscale up` re-established; or next call initiation → `tailscale up` attempted; status shown in Diagnostics.
- **Done when:** Process death detected; UI updates to `disconnected`; Recovery on app foreground or next call; No crash; Call continues (possibly over different transport).

### Plan 07-02: Cellular-Only Tailscale Behavior (No WiFi)
**Task 1:** User has no WiFi available — only cellular data (4G/5G).
- Task 2: Tailscale works over cellular — Tailscale SDK handles cellular IP addresses natively; some OEMs or carrier networks may throttle or block Tailscale UDP traffic; Tailscale fallback to TCP or relay mode may engage.
- Task 3: App behavior: same as WiFi — `tailscale up` establishes; ICE candidates gathered on cellular IP; Audio/Video flows if bandwidth permits; may be lower quality on poor cellular.
- Task 3: User visible: Diagnostics shows `Tailscale: verbunden (Mobilfunk)`; optional lower-quality indicator; Toast "Tailscale über Mobilfunk — falls die Qualität leidet, wechseln Sie ins WLAN" (configurable).
- **Done when:** Cellular-only Tailscale works; UI shows correct status; User informed about quality implications.

### Plan 08-03: Tailscale + Multi-Device Call Scenarios
**Task 1:** attended transfer with Tailscale active: Device A (answering device) has Tailscale path established; Device B (transfer target) also needs Tailscale path.
- Task 2: When Device B joins the call (attended transfer: consult + merge), Device B establishes its own independent Tailscale path (same Auth Key, new Tailscale session).
- Task 3: Both Tailscale paths coexist at PBX; media from both streams mixed; each device's audio independent.
- Task 3: If Device B was already in call and receives attended transfer target: Device B's existing Tailscale path continues; new Tailscale path for the transfer target established; no conflict.
- **Done when:** attended transfer with Tailscale: both devices have independent paths; media mixes at PBX; no key conflicts; call quality preserved.

### Plan 08-05: Quality of Service — Bandwidth & MTU Considerations
**Task 1:** Tailscale has MTU overhead (~20-60 bytes); on constrained networks (poor cellular, satellite), this may affect QoS.
- Task 1: Detect MTU issues: Packet loss, jitter, or audio quality degradation reported by user.
- Task 2: App does not directly control Tailscale MTU, but can monitor QoE; if user reports poor call quality on cellular + Tailscale: Diagnostics shows warning "Tailscale auf Mobilfunk: Qualität möglicherweise eingeschränkt — WLAN empfohlen".
- Task 3: No direct configuration UI for MTU; recommendation to user: use WLAN for Tailscale calls if cellular quality is poor.
- **Done when:** User reports quality issues → Diagnostics warns; WLAN recommended; no UI config change needed; optional: future Phase 6 may add MTU configuration.

## Exit Criteria

- Key expiration workflow: detected → rotated → transport re-enabled
- Process death: detected → UI updates; recovery on app foreground or next call
- Cellular-only: Tailscale works; UI warns about quality if needed
- Multi-device attended transfer: both devices independent paths; no conflicts
- QoS awareness: user warned on cellular; WLAN recommended; no UI config needed (Phase 6 may add)
